# ClawHub installation uses a native HTTP and ZIP adapter

Status: accepted

ClawHub's official `clawhub` CLI cannot satisfy the approved pinning gate: archive entries install correctly at an explicit `--version`, but GitHub-backed entries cannot be pinned to a caller-supplied commit, and sampled GitHub-backed entries are pending-scan suspicious and require the forbidden `--force`. ADR-0034 therefore paused ClawHub installation and required a separate decision before a native adapter. The anonymous ClawHub read API supplies what installation needs without the CLI: a resolver for GitHub-backed entries, a ZIP download for an explicit archive version, per-file SHA-256 lists for that version, and a folder content hash for GitHub-backed resolution. Skills Box will install and update ClawHub skills through a native HTTP and ZIP adapter with no `clawhub` CLI dependency, while keeping Marketplace records and local publication unchanged.

Archive entries download `GET /api/v1/download?slug=…&ownerHandle=…&version=…` at the reference resolved at confirmation, extract in an isolated staging directory, and verify the exact file set and per-file SHA-256 from `GET /api/v1/skills/{slug}/versions/{version}`. Only the registry-generated `_meta.json` may be an extra, and its version must match. GitHub-backed entries resolve `repo/path/commit/contentHash`, download the pinned commit from GitHub codeload, extract only the resolver's subpath, and compare the folder content hash with the resolver value before publication. That hash scheme is undocumented, so it is a hard gate: if the app cannot reproduce it and match sampled entries, GitHub-backed installation stays explicitly blocked rather than falling back to the CLI or claiming archive-only support silently. Installation reads skill-level `moderation` and version-level `security` at install time; explicit suspicious or malware results block with the canonical link and no force path, so pending-scan GitHub-backed entries remain uninstallable until upstream clears them. Browsing and detail still do not display scan fields.

Publication reuses the source-neutral `MarketplaceInstallation` pipeline: backups, canonical replacement, record writes, baselines, Agent attachments and post-publication verification are unchanged. The ClawHub plan supplies only its staged root and record data; execution uses the existing native mutation path instead of a CLI command. Archive records keep the semver reference; GitHub-backed records keep the 40-character commit and `repo/path/commit/contentHash` diagnostics. Updates compare the recorded reference with a newly resolved one; the same reference is current even if upstream content changed, and local baselines detect local edits only.

Considered alternatives were an archive-only CLI channel, rejected as a silent narrowing that still depends on Node and cannot cover GitHub-backed entries; routing GitHub-backed entries through the Git install flow, rejected in ADR-0034; and mirroring packages into App data, rejected for compliance and staleness. The native adapter gives ClawHub installs the same identity and lifecycle as other Marketplace sources, but adds a ZIP and codeload attack surface, depends on an undocumented resolver and hash scheme, and cannot prove package provenance: the download endpoint has no digest and its per-file hashes are not a signed release contract. The adapter therefore enforces strict extraction bounds, fails closed on verification errors, and persists packages only in temporary staging. This decision supersedes the CLI-specific parts of the [ClawHub marketplace specification](../../.scratch/clawhub-marketplace/spec.md) (decision 20 and the CLI dependency rows), and extends ADR-0001 with a second source-specific native mutation exception alongside ADR-0030. Upstream evidence remains in the [contract research](../../.scratch/clawhub-marketplace/research/01-clawhub-contract.md) and the [CLI gate record](../../.scratch/clawhub-marketplace/research/02-clawhub-cli-feasibility.md).
