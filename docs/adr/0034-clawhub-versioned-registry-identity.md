# ClawHub installations use versioned registry records, not Git identities

Status: accepted

ClawHub catalogs versioned `SKILL.md` bundles and resolves installation through its own registry: hosted entries download a ZIP, while GitHub-backed entries resolve to a fixed 40-character commit and subpath with a content hash. The official installer is not a generic `git clone`, and GitHub-backed entries commonly expose no semver version or downloadable archive through the plain detail endpoints. Skills Box therefore treats ClawHub as a Marketplace source whose installations are application-owned Marketplace records keyed by `owner/slug` and the resolved Market reference — a semver version for archive entries, a commit for GitHub-backed entries. ClawHub installations do not merge with Git installation identities: the same upstream repository installed directly through the Git entry or skills.sh remains a different installation identity, and existing same-name conflict rules govern local coexistence. Entries whose `install.kind` is `skills-sh` are excluded from ClawHub search results. The catalog list endpoint does not expose `install.kind`, so such entries are shown normally there (spec R7-Q4); a detail-time exact classification identifies them and redirects to the skills.sh source instead of offering a ClawHub installation.

The alternative of routing GitHub-backed entries through the Git install flow would unify those identities with skills.sh, but it would discard ClawHub's pinned commit and split one source across two identities, two update semantics, and two conflict paths. Restricting installation to GitHub-backed entries would preserve Git identity at the cost of roughly half of the observed official-feed entries, including many OpenClaw-native skills, contradicting the source's purpose. A native HTTP plus ZIP adapter would verify content more directly than the official CLI, but it introduces a new download-and-extract mutation path outside ADR-0001's CLI boundary and depends on an undocumented resolver. The first version therefore uses the official `clawhub` CLI as an optional dependency with isolated staging, an explicitly requested version, no automatic `--force`, and independent staging verification. Version pinning must be proven in isolation: if the CLI does not honor the requested reference or the result cannot be verified, ClawHub installation pauses and a native adapter is evaluated separately rather than switching silently.

Updates compare the resolved reference recorded at installation, not mutable same-version content: a different semver version or commit is an update candidate, while same-version archive content replacement remains outside the feature, following ADR-0030. Resolved commits and content hashes are retained for diagnostics only. Browsing stays online and session-scoped; the complete product behavior, dependency failures, compliance constraints, and acceptance criteria are recorded in the [ClawHub marketplace specification](../../.scratch/clawhub-marketplace/spec.md), with upstream evidence in the [contract research](../../.scratch/clawhub-marketplace/research/01-clawhub-contract.md).
