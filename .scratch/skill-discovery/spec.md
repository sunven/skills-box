## 目标

用户已有安装来源在上游增加 skill 时，应用能够自动发现并在应用内展示。发现与 Update check 是不同操作：发现观察来源中的可用 skills，Update check 比较已有 Managed skill 的版本指纹。Install 和 Update 继续由用户手动选择和执行。

## 已确定决策

第一轮 Q1–Q3，用户于 2026-11-02 回复「按推荐」：

1. **来源**：第一版从已有安装记录获取来源，覆盖 GitHub、CNB 等公开 HTTPS Git 来源。单独订阅没有安装记录的来源不在第一版范围内。
2. **首次发现**：展示首次扫描时已经存在、尚未安装的项。例如来源有 60 个 skills、已安装 20 个，其余 40 个可在发现列表中展示。
3. **新增含义**：首次成功发现来源建立观察起点；之后新出现的 skill 标记为「新增」。首次发现时已有的未安装项不算新增。
4. **提醒**：应用内发现列表与新增数量提示。第一版不增加系统通知或关闭应用后的后台扫描。

第二轮 Q4–Q8，用户于 2026-11-02 回复「按推荐」：

5. **跨 Scope 范围**：统一收集 Global 与所有已注册 Project 的安装来源，按来源去重。同一个来源不因多个 Scope 使用而重复获取。
6. **默认分支**：Source discovery 跟随来源默认分支；已有 Managed skill 的 Update check/Update 仍遵循 Lock entry 中的安全 ref。
7. **调度**：启动时扫描到期来源，新安装来源立即扫描，之后每六小时扫描，保留手动入口。近期扫描过的来源不因重启无条件重新请求。
8. **停止扫描**：扫描范围内最后一条该来源的安装记录移除后，该来源不再自动扫描；历史保留和恢复行为见第四轮决策。
9. **可发现范围**：第一版保持与现有 Install preview/Install 可识别、可安装的范围一致。不扩展任意深层目录，也不扩展现有安装能力。用户已获知根 skill 和深层目录扫描限制。

第三轮 Q9–Q14，用户于 2026-11-02 回复「按推荐」：

10. **发现入口**：顶部独立「发现」入口及应用级页面，显示各来源结果和新增数量。选择发现项安装时进入现有向导，默认以当前 Scope 为目标，仍由用户确认 Scope 和 agents。
11. **候选身份**：以来源和大小写不敏感的 skill 名称识别同一项。目录移动不算新增，名称变化算新项。同一来源同名项受现有按名称选择安装的限制，不新增按路径挑选能力。
12. **手动扫描**：手动扫描立即检查上游、绕过六小时扫描间隔，但继续复用相同版本的已有缓存并遵守限流恢复时间。
13. **失败处理**：失败保留 Source catalog、新增状态和上次成功时间，不建立或覆盖首次发现基线。自动重试遵守六小时尝试间隔与限流恢复时间，不立即重试。
14. **来源较多**：按最久未扫描的来源优先，分批处理并显示进度。剩余来源自动续扫，限流时暂停排队获取，避免固定排序导致部分来源永久被跳过。
15. **Project 暂不可读**：Project root 或 lock 暂不可读时，沿用该 Project 上次成功读取的来源信息，继续扫描已知来源、保留结果并显示警告，恢复后校正。成功 Relocate/Forget 撤销旧根关联；旧扫描完成不能恢复已撤销的来源关联。

第四轮 Q15–Q18，用户于 2026-11-02 回复「按推荐」：

16. **已安装范围**：发现页以所选安装 Scope 判断已安装，默认展示该 Scope 未安装项，支持切换「全部」。例如全局已安装、Project 尚未安装时，Project 仍能看到该项，并标注其他 Scope 的安装情况。不同来源同名占用显示为安装冲突，不误标成同一项已安装。
17. **已读与数量**：新增标记和入口数量在应用内按 Discovered skill 统一计算，切换 Scope 不重新计数。查看单项详情或通过应用安装成功后清除该项提醒，提供「全部已读」；仅打开列表不自动清除所有提醒。
18. **忽略**：忽略项从默认列表和提醒中隐藏，可在「已忽略」中恢复；忽略视为已处理，恢复后作为已读项显示。重复扫描或同项内容变化不重新提醒。状态在应用内共享。
19. **历史与重新出现**：来源没有安装记录时停止扫描并隐藏，保留观察历史及用户状态。以后重新安装该来源按历史比较，离开期间首次出现的新名称仍会被发现，旧项不制造新的新增事件。上游移除的项隐藏，同名项回归沿用历史。历史跨重启保留。

## 已调查事实

现有预览只提供 name、description、group 和目标 Scope 的冲突，不提供源路径。来源归档获取和 GitHub token 认证可以复用，但扫描目录规则并不是「找到所有 `SKILL.md` 即可」。完整依据见调查记录。

当前 Update check 的 active-Scope 生命周期、项目 revision 失效保护及手动更新流程继续作为现有行为；本访谈没有批准改变这些流程。

## 扫描契约的实施依据

补充只读调查确认，pinned CLI 的 GitHub blob 和 clone 两条扫描路径在根 skill、插件声明、文件名大小写、重名及回退方面不同，并且实际路径会受下载是否成功影响。直接原生枚举归档无法保证与现有 Install preview 的实际列表一致；symlink 和 `export-ignore` 也可能使归档与 clone 的材料不同。

依据已确认的 Q8，第一版设计以现有 CLI 只读预览的实际名称、描述、分组作为 Source catalog 的内容依据：先用原生版本查询检查默认分支，版本未变且有有效 catalog 时复用已有目录；首次扫描或版本改变时调用共享的只读预览执行/解析能力。提取目录内容时不把某个 Scope 的预览冲突混入来源目录；冲突仍由目标 Scope 的安装流程判断。

GitHub 版本查询使用已实现的 SettingsService/GitHubApiClient 认证，保持页面 token → 启动环境 GITHUB_TOKEN → 匿名的优先级。继续遵守当前 token 只发送到原生 api.github.com 请求的边界，不传给 CLI 子进程。CLI 的特殊 GitHub 预览路径会自行请求匿名 Trees，失败可回退 clone；不能声称所有发现网络请求都带 token。

该选择意味着初次发现和来源版本变化时需要已有 Node/npx/Git 运行环境；原生版本查询和读取已持久化目录不依赖 Node。现有 source archive 缓存不能透明替代 CLI 自己克隆；目录未变时通过复用 catalog 避免重复预览，不能宣称变更后的预览复用了原生归档文件。缺少运行环境或预览失败按失败行为保留上次目录，不发布成功空列表。

安装前继续执行当前只读预览；目录缓存不能直接作为安装计划。如果某个缓存发现项已经不在实际预览中、名称校验失败或有不可区分的重名，不直接启动该项安装，并给出可重新扫描的提示。预览与缓存不一致时使对应 catalog 需要重新验证，防止相同版本缓存持续掩盖不一致。

## 具体行为

### 来源与安装状态

- 只收集 Global 与已注册 Project 的 lock 中可解析的公开 HTTPS Git 来源。没有来源的 Unmanaged skill 不建立来源；Stale lock entry 仍是一条已有安装记录。
- 使用共享 SourceSpec/Update target 的来源解析和身份规则：GitHub 身份忽略大小写；通用 Git 保留路径大小写。发现忽略 lock 的 ref，读取默认分支。
- 每个 Scope 的来源快照关联当前 Project revision。暂不可读只沿用同一有效 revision 的上次快照；成功 Relocate/Forget 立即撤销旧快照。
- 明确撤销后的 Source 不因持久化清理失败或旧请求完成重新出现。若其他 Scope 仍使用该 Source，来源目录继续有效。
- 安装状态从当前 Scope 的 lock 与文件系统读取。Managed skill 的 canonical 或 agent copies 存在时可显示已安装；只有 Stale lock entry 时显示记录异常/占用；Unmanaged 同名项和其他来源同名项显示冲突。Scope 不可读时显示未知并禁用该 Scope 的安装入口。
- 其他 Scope 已安装仅作为说明，不隐藏当前 Scope 未安装项。不同 Source 的同名发现保持独立；实际安装冲突仍由现有安装门禁最终验证。

### 新增、已读与忽略

| 事件 | 目录与历史 | 提醒 |
|---|---|---|
| 某来源首次成功预览 | 记录当次全部项为已观察；允许明确成功的空列表建立基线 | 当次已有项不标新增 |
| 初次获取或预览失败 | 不建立基线、不记录空目录 | 显示失败；无伪造新增 |
| 之后首次观察到新名称 | 加入目录和历史，记录首次发现 | 产生一条未读新增 |
| 同名内容变化、仅目录移动或大小写变化 | 更新展示元数据，沿用身份与用户状态 | 不制造新的新增事件 |
| 查看单项详情 | 保留目录，标记该项已处理 | 清除该项未读提醒 |
| 通过应用安装成功 | 仅标记实际成功项已处理；部分失败项保留原状态 | 成功项不再计数 |
| 全部已读 | 处理命令执行时所有活跃、可用项的未读提醒，不受当前 Scope/列表筛选限制 | 命令之后才发现的新项仍可未读 |
| 忽略 | 标记已处理、已忽略，保留历史 | 默认列表与数量均排除 |
| 恢复忽略 | 清除忽略状态，维持已处理 | 返回普通列表，不重新标新增 |
| 来源没有安装记录 | 停止扫描并隐藏，保留目录、历史与用户状态 | 不贡献入口数量 |
| 来源重新被使用 | 立即作为新活跃来源检查，按原观察历史比较 | 从未见过的名称产生新增；已读/忽略不重置 |
| 成功预览确认某项移除 | 从当前目录隐藏，保留观察及用户状态 | 不贡献入口数量 |
| 同名项重新出现 | 沿用历史，不建立新的首次发现事件 | 已处理项不重提醒；尚未处理的旧提醒仍可继续显示 |
| 本地卸载某项但来源仍活跃 | 安装投影变为未安装，来源观察历史保持 | 本地卸载本身不产生上游新增 |

入口数字统计活跃 Source catalog 中仍可用、未忽略、未处理的 New skills，按 `(source identity, name identity)` 去重。它与 Scope、搜索及列表筛选无关。

扫描发布必须合并当前已读/忽略状态；不能拿开始扫描时的用户状态覆盖扫描期间的用户操作。

### 发现页与安装入口

- 顶部「发现」入口及应用级新增数量；普通进入时默认「当前 Scope 未安装」。页面支持「全部」「新增」「已忽略」及名称/描述搜索、来源筛选。
- 页面提供「查看全部新增」入口，使应用级数量中的每一项都能查看；「新增」视图不因当前 Scope 已安装而隐藏项。切换 Scope 不清除提醒。
- 来源区显示名称/地址、扫描状态、上次尝试和上次成功时间；条目显示名称、描述、可选分组、安装状态和提醒状态。失败时仍展示上次成功的目录并标注来源失败。
- 单项详情展示名称、描述、来源、分组和各 Scope 的安装状态；首次版本不增加远程内容文件浏览器。
- 点安装后，把 Source 和单项名称传入现有 Install wizard，运行实际预览并仅预选用户点击的项。用户继续选择 Scope/agents 和确认安装，不自动执行 Mutation task。
- 切换目标 Scope 时沿用当前安装向导的 Scope 校验，并保留来自发现项的来源/名称意图以便重新预览。关闭向导返回发现页；普通手动安装入口保留当前行为。
- 页面切换不停止应用级扫描；回到主列表沿用现有 Scope 切换和筛选/选中行为。后台扫描错误通过来源状态展示，不弹出安装或更新确认框。

## 记录与调度设计

### 持久化

在 app data 中新增版本化 `discovery.json`，作为 Discovery history 的辅助记录，不修改安装 lock：

- Scope 来源快照：Scope ID、Project revision、上次成功读到的规范来源。
- Source 观察记录：规范来源、是否建立过基线、当前 catalog、适用的 CLI/解析契约版本、已验证来源版本、上次尝试/成功时间、来源状态。
- 每个发现身份的历史：首次观察、是否属于基线后发现、已处理和已忽略状态；目录移除不删除历史。
- 已知限流恢复时间和展示诊断；不存储 token 或 CLI 环境。

原子写入；读取校验版本、身份与合理大小上限。文件不存在是未初始化；已有文件损坏/版本未知/读取失败需显式报错并保留原文件，不能静默当成全新历史。用户状态写入失败不报告已读或忽略成功。扫描结果逐个 Source 保存，完整 run 不要求一次性成功。

安装记录和注册表仍决定来源是否有效；仅凭旧 discovery.json 不能读取已 Forget 的 Project root，也不能恢复旧 revision 的来源关联。进程内发布以当前状态合并，防止文件覆盖丢失用户操作。

### 扫描生命周期

1. 应用就绪、相关来源快照可用且没有变更任务阻挡新自动扫描时，收集来源并检查到期项。新活跃来源立即进入队列。应用内安装/卸载和 Project 生命周期成功后重新收集；应用外修改在下一次已有数据刷新或定时收集时发现，不增加新的文件监听器。
2. 自动扫描以每个 Source 最近尝试时间为六小时锚点，结合限流恢复时间。近期尝试过的来源不因重启或切换 Scope 重扫。手动扫描绕过六小时锚点，仍遵守当前认证上下文的限流。
3. 使用原生 GitHub/Git 版本查询。有效 catalog 与契约版本均匹配、来源版本未变时复用；首次、版本改变或 catalog 已失效时调用共享只读预览。
4. 预览读取默认分支，预览前后版本查询若证实分支发生变化，本次不把不确定版本结果绑定为成功 catalog；保留旧结果并等待下次尝试，不无限重试。
5. 每批最多 20 个来源，并发最多 4；按未扫描/最久未扫描优先。一轮中每来源至多尝试一次，剩余来源分批继续。排队、限流暂停或被撤销的项不伪造成功，也不写成已完成的尝试。
6. 原生版本查询遵守现有 API/Git 请求期限，预览 CLI 保留现有 60 秒上限。run 通过异步事件/状态返回进度，不能把整轮放入现有 30 秒普通读取期限而导致大来源集合永久扫不到。
7. 成功逐来源合并并原子保存；失败保存诊断和尝试时间，保留上次 catalog/成功时间。解析失败、超时、运行环境缺失、取消等均不能变成成功空列表。
8. 同时只有一个应用级发现 run，自动、手动和 React StrictMode 不重复启动同一轮。页面/Scope 切换继续该 run；退出应用取消队列及进程组，保留已经提交的结果。
9. 来源活跃生命周期和 run 标识参与发布校验。Source 停用再恢复、Project A→B→A、Forget 后重新注册均不能让旧扫描替新来源关联发布。扫描网络与 CLI 运行不持有 Mutation permit 或长时间注册表锁。

限流使用结构化恢复时间，调度不解析 UI 错误文字。可用的 `x-ratelimit-reset` / `Retry-After` 控制 GitHub 获取暂停；其他 Git 来源仍可处理。401 不降级匿名。新凭据配置或认证测试已证实认证上下文改变时，不以旧上下文的冷却阻止手动重试，旧请求也不能覆盖新上下文的限流状态。未知恢复时间按六小时错误退避处理。

## 验收条件

## 范围与限制

第一版不增加手动来源订阅、SSH/私有仓库认证、ref 选择、任意深层扫描、系统通知、关窗后台扫描、自动安装/更新或远程文件内容浏览器。发现范围沿用 pinned CLI，初次或变更后的预览需要 Node/npx/Git；GitHub token 只用于原生 API 认证，CLI 自行请求的网络路径不继承它。

此方案通过定期观察发现新增，不承诺保留两次成功扫描之间曾出现又消失的短暂项。Discovery history 损坏时需显式恢复历史，不能保证从安装 lock 重建已读/忽略决定。
